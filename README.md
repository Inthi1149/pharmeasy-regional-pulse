\# PharmEasy Regional Pulse



\## Run from a Fresh Clone



From PowerShell in the repository root, run these commands in order:



```powershell

py -m pip install -r requirements.txt

py run\_pipeline.py

py -m streamlit run app.py

```



The pipeline regenerates and validates the project from the supplied deterministic dataset generator through cleaning, SQLite construction, SQL analysis, month-to-month metrics, CII report generation, and review-gate acceptance checks.



Pipeline order:



`generate\_dataset.py -> clean\_data.py -> build\_db.py -> queries.py -> metrics\_engine.py -> draft\_report.py -> review\_gate.py`



No API key or paid service is required.

The official deterministic generator produces 2,159 raw rows.



The cleaning pipeline removes 59 exact duplicate rows, leaving 2,100 clean orders. After duplicate removal, 48 missing category values and 94 missing `profit\_inr` values are repaired, leaving zero missing values in those fields.

\## Metric Rule



Month-to-month percentage change is calculated as:



`(current - previous) / previous \* 100`



If the previous value is zero, `compute\_percentage\_change\_v1()` returns `0`.



A region is operationally flagged only when:



`abs(change) > 8`



The comparison is strict: exactly 8% is not flagged. The 8% threshold is an operational-alert business rule, not a statistical-significance test.



For April to May, the flagged regions are Hyderabad, Warangal, Visakhapatnam, Guntur, Tirupati, Karimnagar, and Bengaluru.



For May to June, the flagged regions are Hyderabad, Warangal, Vijayawada, Visakhapatnam, Guntur, Tirupati, and Karimnagar.



Nellore is not flagged in either transition.

\## Human Review and Reliability



`review\_gate\_v1(report, decision, reviewer\_note="")` accepts only:



\- `approve`

\- `edit`

\- `reject`



Only `approve` allows downstream use. Each call appends an audit record to `audit\_log.jsonl` containing `timestamp`, `run\_id`, `region`, `decision`, and `reviewer\_note`.



The test harness exercises all three decision paths, prints the before/after report state for each path, and verifies that an invalid decision is rejected.



The reliability workflow documented in `reliability\_checklist.md` is:



\*\*Safety Check -> Validation -> Critique/Refine -> Human Sign-off\*\*
